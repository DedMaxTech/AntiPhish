# Документация проекта AntiPhish

Версия 2.1

AntiPhish - локальная программа для анализа писем, ссылок, сайтов и вложений. Она исследует содержимое, при выбранном сетевом режиме проходит доступные переходы и объясняет результат конкретными признаками. Основной сценарий - российские бренды и русскоязычная почта с осторожным отношением к ложным срабатываниям.

Документ описывает действующую реализацию, её запуск, обслуживание, интеграцию и сохранённые проверки. Анализатор работает через GUI, CLI, Python и внутренний REST API. Во всех точках входа используются общий Analyzer и одинаковые условия вердикта. Самостоятельных тяжёлого и лёгкого контуров, нового отдельного экспорта обобщённых правил и автоматического почтового карантина нет.

## 1 Возможности системы

На вход принимаются EML, исходный MIME, HTML, URL, PDF, Office-документ, ZIP и изображение. EML сохраняет заголовки, текстовые и HTML-части, кодировки, встроенные картинки и вложенные сообщения. Обычный текст тоже можно исследовать, но часть сведений об исходном письме уже потеряна. Пакетный запуск принимает папку, ZIP или TAR и выдаёт отдельный результат для каждого поддерживаемого объекта.

Программа извлекает адреса из текста, HTML, документов и QR-кодов; раскрывает известные обёртки ссылок, редиректы и опубликованные таблицы. Для страницы определяются заявленный сервис, формы, типы запрашиваемых данных и предполагаемый получатель. Вложения проверяются структурно: макросы и скрипты документов не выполняются.

Проверка сочетает правила содержимого, локальные репутационные списки, каталог брендов, сходство с образцами и дополнительные модели. Эти источники имеют разную силу. Упоминание компании, логотип или поле пароля не равнозначны подмене сервиса; для сильного решения нужна связанная картина атаки либо подтверждённый индикатор.

Каталог содержит 126 активных идентичностей: банки, государственные сервисы, маркетплейсы, доставку, страхование, магазины и деловые продукты. Учитываются варианты русских названий, кириллица, компенсации, инвестиционные предложения, угрозы аккаунту и переход в мессенджер. Это не полное покрытие всех организаций и способов входа. Из 175 нормализованных названий заказчика у 47 найдено совпадение с именем или алиасом активной записи; такое совпадение ещё не измеряет качество распознавания.

Результат содержит причины, URL, страницы, формы, маршруты, вложения, ограничения и время этапов. Его можно просмотреть в GUI, получить в JSON, сохранить в историю или использовать во внутренней интеграции.

Практический сценарий - предварительная проверка полученного письма: пользователь выбирает файл и настройки, читает причины, затем решает, нужен ли дополнительный обход или ручная проверка. Для периодического просмотра каталога подходит batch; для вызова из другой программы - Python или API. Одинаковый формат отчёта позволяет сопоставить результаты этих запусков без отдельного преобразования.

## 2 Профили и сетевые режимы

Профиль определяет состав извлечения, сетевой режим - разрешённый способ загрузки сайтов. Это независимые настройки: deep не включает браузер автоматически, а browser доступен без языковой модели.

| Профиль | Что выполняется |
|---|---|
| fast | Разбор с уменьшенными лимитами, без OCR, QR и изображений внутри документов. |
| quality | Обычный полный разбор, вложения, QR и локальный OCR. |
| deep | Quality, фактическое извлечение Qwen и визуальные наблюдения SigLIP2 при подходящем изображении. |

| Сеть | Поведение и границы |
|---|---|
| offline | Только переданные материалы и локальные базы; неизвестный конечный сайт не загружается. |
| http | Проверяемые GET-запросы и редиректы; JavaScript не выполняется. |
| browser | Отдельный браузерный контекст, динамический DOM и ограниченный сценарий формы. |

Одиночный CLI и GUI по умолчанию используют quality/http. Batch, REST API и прямой Python Analyzer по умолчанию работают offline. При интеграции обе настройки лучше указывать явно: иначе одно и то же письмо через разные точки входа может получить разный объём сетевой проверки.

Профили меняют доступные факты, а не порог блокировки. Fast может не увидеть адрес в картинке, а browser - найти форму, отсутствующую в исходном HTML. Условия PHISHING при этом общие. Результаты разных профилей нельзя сравнивать без учёта выполненных этапов.

Для ручной проверки обычно подходит quality/http. Offline позволяет исследовать локальные данные без обращения к ссылкам. Browser полезен для клиентского JavaScript, deep - для дополнительного смыслового анализа. Все тяжёлые этапы на каждом письме значительно увеличивают стоимость обработки. Отсутствующая модель не скачивается автоматически и отражается как ограничение, если её работа была запрошена.

## 3 Как проходит анализ

Analyzer принимает данные и настройки, запускает извлечение и собирает общий отчёт. Из письма выделяются текст, HTML, адреса, вложения, изображения и сведения о заголовках. Затем исследуются доступные переходы, формы, идентичность сервиса, базы и дополнительные модели. Окончательное решение принимает `policy.py`.

Последовательность выглядит так:

`Вход → извлечение → маршрут → страницы и формы → базы и модели → решение → JSON`

Каждый факт связан с источником и областью страницы. Нельзя взять название банка из письма, поле пароля из другого сайта и адрес из третьего и объявить их одной формой. Глобальные сведения о брендах остаются описанием, а доказательство проверяется в контексте конкретного действия.

MIME разбирается стандартными средствами Python. HTML и XML читаются структурно; Office проверяется по XML, отношениям частей, ссылкам и формулам. Из PDF извлекаются текст, поля, ссылки и действия. Quality/deep используют OCR для доступных изображений и сканов. Старые бинарные документы исследуются ограниченно; это не полноценное открытие в Office.

Архивы читаются без распаковки по недоверенным именам. Контролируются размер, глубина, число элементов и сжатие. Зашифрованная или повреждённая часть отмечается явно. XML не получает доступ к внешним сущностям.

| Ограничение обычной конфигурации | Значение |
|---|---:|
| Вход и отдельное вложение | 50 и 40 МиБ |
| Суммарное извлечение | 200 МиБ |
| Архив | 2 000 элементов, 200 МиБ, глубина 3, коэффициент до 100 |
| URL и формы | 500 и 100 |
| Сетевые страницы и глубина | 12 и 4 |
| Сетевой бюджет | 45 с |
| HTTP | 7 редиректов, 10 МиБ ответа, до 12 с на запрос |
| PDF и изображения | 100 страниц, до 30 млн пикселей на изображение |
| OCR | До 6 вызовов, сторона до 1 800 пикселей, бюджет 12 с |

Это ограничения объёма работы, а не общий жёсткий таймер для любого письма. Разбор, старт браузера и модель добавляют время; начатый OCR-вызов не обрывается точно по границе бюджета. Fast использует меньшие пределы части операций.

## 4 Ссылки и путь до целевого сайта

Фишинговая цель может скрываться за легальным документом, таблицей, сокращателем или промежуточной страницей. Поэтому исследуется маршрут «письмо → ссылка, QR или вложение → страница → форма → получатель». Хорошая репутация первого домена не устанавливает безопасность следующего шага.

Посещённые объекты различаются по полному URL. Две страницы одного сайта могут иметь разное назначение. При загрузке сохраняются значимые параметры и их порядок, чтобы не ломать подписанные адреса. Для отображения чувствительные значения маскируются; служебный адрес навигации не включается в публичный JSON.

Очередь отдаёт приоритет действиям пользователя. CSS, изображения и другие ресурсы оформления не считаются обычными переходами. Action формы учитывается как получатель и не посещается ради отправки. Токенизированные ссылки подтверждения действия также не обходятся.

Поддерживаются HTTP-редиректы, meta refresh, буквальные JavaScript-переходы, некоторые base64/hex/Unicode/percent-кодировки и `String.fromCharCode`. Раскрываются Google /url, Microsoft SafeLinks, VK /away.php и отдельные AMP-обёртки. В опубликованных Google Sheets извлекаются ссылки ячеек и промежуточный `pageUrl`. Вычисляемый сценарий может требовать browser.

В исходном примере Wildberries обнаружен переход через опубликованную таблицу, Google /url и сокращатель. Это подтверждает раскрытие доступного промежуточного маршрута; свойства недоступного исторического конечного сайта не предполагаются.

Закрытый документ, обязательный вход, CAPTCHA, истёкший адрес и географическое ограничение могут оборвать цепочку. Отчёт показывает, до чего дошёл анализатор. Неизвестный следующий шаг не считается безопасным, но само наличие промежуточного облачного сервиса не является доказательством атаки.

## 5 Анализ сайтов форм и активного содержимого

У страницы сохраняются заголовок, DOM-отпечатки, формы и типы внешних ресурсов: изображения, скрипты, iframe, CSS и favicon. Есть структурный отпечаток DOM с вложенностью без текста и атрибутов. Для формы доступны XPath, безопасное описание полей и получатель без пользовательских значений.

Идентичность определяется по заголовку, заметным заголовкам, легендам форм и компактному тексту входа. Навигация, footer и отдельные кнопки сторонней авторизации не должны устанавливать владельца формы. Чувствительные типы включают пароль, OTP, карту/CVV, секрет кошелька и персональные данные. Скрытые, отключённые, readonly-поля, закрытые dialog и template не считаются обычным активным вводом.

Получатель извлекается из action, допустимой отправки на текущую страницу или конкретной статической связи JavaScript с полями. Это объявленный маршрут сбора, а не доказательство успешной передачи настоящих данных. Домены сравниваются с каталогом с учётом назначения: пользовательский хостинг не равнозначен официальному месту авторизации.

PDF исследуется по реальным словарям действий и объектам, включая сжатые JavaScript-потоки. Фиксируются JavaScript, Launch, SubmitForm, ImportData, удалённые переходы и встроенные файлы. Упоминание этих слов в обычном тексте не считается действием. Чтение имени и отправка обычной анкеты не приравниваются к отправке пароля.

VBA разбирается oletools в отдельном процессе: до 8 с, контроль памяти 512 МиБ и объёма вывода. Общий бюджет активного содержимого - 12 с. Извлекаются отпечатки модулей, URL, автозапуск, сеть, запуск процессов и динамический код; макрос не выполняется.

Буквальный `document.write(atob(...))` и некоторые HTML-присваивания восстанавливаются без исполнения с ограничением вложенности. Такие формы помечаются `decoded-script` и сами не доказывают выполненный DOM-сценарий для PHISHING.

Полезно различать три ситуации: в документе упомянут JavaScript, у PDF действительно есть действие JavaScript, а действие обращается к чувствительным данным и внешнему получателю. Это разные по силе наблюдения. Аналогично автозапуск VBA требует внимания, но обычная деловая книга с макросом не должна получать подтверждённый фишинг только за наличие модуля.

## 6 Правила принятия решения

Решение представляет собой условия над наблюдаемыми фактами. Файл `resources/rules.json` служит описанием; его редактирование не заменяет изменения исполняемой политики.

| Вердикт | Смысл |
|---|---|
| PHISHING | Подтверждённый действующий индикатор либо связанная подмена сервиса и сбор секрета. |
| SUSPICIOUS | Существенное основание для проверки при недостатке сильного подтверждения. |
| NOT_DETECTED | Достаточные признаки не найдены в исследованной части. |

### 6.1 Основания сильного решения

Первый путь - точное совпадение с подтверждённым URL или хешем. Корпусный объект с непроверенной меткой сохраняется как известный образец, но не становится блокирующим IOC автоматически. Для фидов проверяется полный URL; фрагмент после # не участвует в ключе. Подтверждённость, источник и срок действия имеют значение.

Второй путь - конкретная форма. Нужны достаточно полно исследованная страница, идентичность из DOM, запрос секрета, установленный получатель и несоответствие адресов заявленному сервису. Допускается связанная подмена отображаемого адреса и получателя формы. Факты должны относиться к одной области, а не собираться из независимых страниц.

Неполный обход других ссылок не отменяет уже установленное доказательство. При этом OCR, похожий логотип или восстановленная строка скрипта не подменяют реальную DOM-форму.

### 6.2 Предупреждения и защита от ложных тревог

SUSPICIOUS используется для имитации формы без достаточно установленного получателя, неподтверждённого внешнего сборщика у официальной страницы, общественной репутации, сходства кампании, опасных вложений, макросов и активных признаков отправки секретов.

Правила содержимого учитывают вознаграждение за ответ, сомнительные инвестиции, угрозу аккаунту, перевод в мессенджер, поддельное обновление платежа и завершение перевода. Для восстановления аккаунта и доступа к документам важны действие, идентичность и размещение на пользовательском хостинге. Обычные реквизиты или слова «срочно» и «пароль» не являются достаточным условием.

Кнопка «Войти через Google», платёжные логотипы Visa/Mastercard/«Мир» и учебная статья могут встречаться на легитимной странице. Анализ должен отличать упоминание от владельца формы. LLM, pHash, визуальное сходство, сокращатель, кириллица и метка поставщика самостоятельно не дают PHISHING. Qwen может добавить SUSPICIOUS только при валидных фактах о подмене и запросе секрета/изменении оплаты с точными цитатами.

### 6.3 Полнота проверки

`analysis_status` принимает COMPLETE, PARTIAL или FAILED. COMPLETE означает завершение запрошенных проверок в пределах материалов и лимитов. PARTIAL указывает недоступность или ограничение сети, формата либо модели. FAILED означает, что анализ не выполнен; GUI отображает это отдельно.

Статический и сетевой этапы имеют отдельные состояния. Поэтому статический разбор может завершиться, а общий анализ остаться PARTIAL. Ошибка загрузки не создаёт фишинг и не доказывает безопасность.

Официальная банковская форма с допустимым получателем не должна блокироваться за название банка и пароль. Та же идентичность на чужой странице с установленным сборщиком секрета даёт сильное основание. Подарок через неизвестную таблицу чаще остаётся предупреждением. Для смены реквизитов по переписке может понадобиться доверенная история контрагента, которой анализатор не располагает.

## 7 Локальные базы репутации и образцов

### 7.1 Репутационные списки

Основная KB и фиды разделены. Фиды находятся в `artifacts/knowledge.reputation.sqlite`. Адрес ищется в локальном снимке; удалённый репутационный API на каждое письмо не вызывается. Посещение самого сайта в http/browser - другая операция.

| Источник | Применение | Последний сохранённый объём |
|---|---|---:|
| Phishing.Database | Общественные сведения, предупреждение. | 787 653 |
| OpenPhish Community | Точные подтверждённые URL, возможно PHISHING. | 300 |
| PhishTank | Необязательные verified+online с ключом приложения. | Не включён в пару по умолчанию. |

Объём снимка не равен количеству действующих независимых атак. Возможны устаревшие, повторные и ошибочные записи. Совпадение одной страницы из фида не блокирует весь домен. Ручной индикатор хоста имеет другую область действия и требует отдельного контроля.

Обновление рекомендуется раз в несколько дней. Записи старше семи дней исключаются до успешного обновления; возраст показывается в отчёте. Каждый источник заменяется транзакционно. При сетевой ошибке, неожиданном HTML или подозрительном уменьшении предыдущий снимок сохраняется. ETag записывается, но обязательное условное скачивание не реализовано.

У Phishing.Database лицензия MIT с сохранением уведомлений. [Условия OpenPhish](https://openphish.com/terms.html) допускают личные и независимые исследования, не обслуживающие бизнес-операции организации. «Некоммерческий» не означает разрешения любого организационного внедрения; передача фида третьим лицам требует разрешения. При смене сценария условия проверяются заново. Чужие списки не входят в wheel.

### 7.2 Образцы и шаблоны

Основная SQLite хранит хеши, индикаторы, отпечатки, бренды и происхождение. Точный хеш узнаёт неизменённый объект; для небольших изменений используется сходство поведения. Шаблон объединяет SimHash DOM, SimHash трёхсловных фрагментов и типы чувствительных полей. Текущие расстояния - до 3 бит по структуре и 4 по тексту при совпадающем наборе полей.

Сходство даёт предупреждение, учитывая происхождение, проверенную метку или связанный бренд. Отрицательный образец может отменить похожее предупреждение шаблона, но не независимый IOC или доказанный сбор секрета. Это механизм для повторяющихся ошибок; добавление отрицательной страницы не объявляет безопасными все страницы её домена.

Корпус содержит 396 писем и 556 сохранённых HTML. Метка архива не подтверждает каждый файл: встречаются промежуточные легальные страницы и ошибки. Импорт не дообучает модель и не превращает все 9 913 ранее собранных SHA256 в блокирующие индикаторы. Сборка KB идёт через промежуточную SQLite с сохранением ручных записей и шаблонов.

### 7.3 Непроверенный CSV доменов

CSV хранится отдельно в `knowledge.domains.sqlite`. Принято 22 853 точных хоста; 109 суффиксов и два адреса-примера отброшены. Нормализация учитывает IDNA. Совпадение добавляется в `configuration.domain_context`, не влияет на решение, не распространяется на поддомены и не разрешает collector. Поломка справочника не отключает детектор.

## 8 OCR локальные модели и логотипы

### 8.1 Распознавание текста и QR

RapidOCR использует локальные ONNX-модели PP-OCRv5 с кириллицей и латиницей. OCR работает с MIME-изображениями, сканами PDF и browser-снимками. `setup-ocr` заранее скачивает три файла из RapidAI и проверяет закреплённые SHA256. Runtime ничего не загружает при отсутствии весов. Маленькие tracking-пиксели пропускаются, большие изображения уменьшаются.

QR декодируется отдельно через OpenCV. После неудачного мультидетектора пробуется одиночный, затем инверсия, контраст и бинаризация. Найденный адрес идёт в общий анализ маршрута; QR сам не является опасным признаком.

OCR может путать мелкие и размытые надписи. Его результат не создаёт поле формы и не устанавливает DOM-получателя. Бюджет количества/времени общий для анализируемого объекта; отсутствие распознавания отражается как ограничение, а не как подтверждение отсутствия ссылки.

### 8.2 Qwen и другие языковые модели

Deep использует локальную Qwen3.5-4B. Вход состоит из ограниченных фактов о страницах и формах, выдержки сообщения и HTML, иногда изображения. Ответ содержит признаки запроса учётных данных, изменения оплаты, подмены и до трёх точных цитат. Вход усечён, вывод ограничен 220 токенами; гигантский документ не читается целиком.

Генерация детерминированная. Невалидный JSON и отсутствующие в исходнике цитаты не используются как факты. Это снижает риск выдуманного основания, но не гарантирует иммунитет к инструкциям внутри недоверенного письма. Некорректный ответ означает ограничение модели; он не превращается в безопасный результат.

Совместимый мультимодальный каталог задаётся `ANTIPHISH_LLM_MODEL_DIR`. Используются локальные файлы, Safetensors и запрет remote custom code. Внешний LLM API не вызывается. Альтернативные веса, включая Gemma 3, пока не проверены; поддержка пути не доказывает совместимость любой модели.

Экспериментальный Horizon-Labs phishing-scam-detector-base - multilingual mmBERT 307M с классами legit/spam/fraud и окном 384 токена. Он скачивается `setup-text-model`, включается `ANTIPHISH_TEXT_MODEL_DIR` и добавляет только оценки. По умолчанию выключен. Spam не складывается с fraud; реклама не становится фишингом из-за этой суммы.

На 540 письмах при пороге fraud 0,5 классификатор отметил 8/40 phish и 0/500 benign; при 0,9 - 3/40. Это не основание заменить основной анализ. [Granite URL QLoRA](https://huggingface.co/bengoldberg0/granite-4.2-3b-phishing-url-qlora) не подключён: он исследует только URL, а опубликованный внешний FPR 64% не соответствует цели минимальных тревог. Новые веса и обучение требуют отдельного независимого сравнения.

### 8.3 SigLIP2 и эталоны логотипов

SigLIP2 выдаёт визуальных кандидатов по текстовым описаниям, а новый индекс - по проверенным картинкам. Галерея `manifest.jsonl` содержит `path`, `brand`, официальный `source_url` и `reviewed:true`. Команды `index-logos` и `match-logo` строят индекс и возвращают сходство, область и отпечаток эталона. Deep добавляет наблюдения, если индекс доступен.

Проверены три официальных favicon: Dr.Web, Яндекс, Росгосстрах. Это функциональная проверка, не оценка полного покрытия. Сходство не равно вероятности атаки; самостоятельного блокирующего значения нет. Для обучения детектора областей RTX 4080 достаточна, но нужны рамки, варианты логотипов и отрицательные партнёрские/платёжные случаи. Новая сеть не обучалась.

## 9 Безопасность и данные

HTTP разрешает публичные назначения, проверяет DNS и каждый редирект, закрепляет соединение за разрешённым IP и сохраняет исходные Host/TLS SNI. TLS проверяется. Loopback, локальные сети и непубличные адреса не должны открываться через ссылку письма.

Browser использует временный контекст Edge на Windows или Playwright Chromium на Linux без пользовательской сессии. GET проходят через защищённый транспорт. Ограничены загрузки, service workers и отправки; WebSocket не подключается, WebRTC отключён. После зависшего JS завершаются только собственные процессы браузера; драйвер сохраняется для следующего объекта.

Для клиентской формы допускаются до трёх шагов на вымышленной почте, пароле и OTP. До заполнения блокируется весь последующий HTTP, включая GET, картинки и beacon. Попытка передать тестовый секрет фиксируется, но не отправляется: `synthetic_only=true`, `transmitted=false`. Серверозависимый следующий шаг может остаться недоступным; произвольные покупки и платежи не выполняются.

Browser требует `I_UNDERSTAND` и создаёт реальные первоначальные GET-запросы: сайт видит факт посещения и IP. Контекст и Docker не равны полной виртуальной машине. Для проверки без обращения к сайтам используется offline.

JSON не содержит целый MIME, HTML и снимки. Однако имя файла, объяснение и модельная цитата могут содержать сведения из письма. История SQLite хранит отчёты, поэтому тоже не считается автоматически обезличенной. Приватные снимки capture-urls требуют отдельной проверки перед передачей; в origin.json остаётся адрес для воспроизводимого разрешения ссылок.

## 12 Установка запуск и обычная работа

### 12.1 Окружение

В подготовленном проекте можно запустить диагностику и GUI:

```powershell
cd D:\Projects\Python\AntiPhish
.\.venv\Scripts\python.exe -m antiphish doctor
.\.venv\Scripts\python.exe -m antiphish gui
```

Doctor показывает базу, браузер, OCR, модели и CUDA. GUI выполняет одну проверку в рабочем потоке, показывает причины и сохраняет JSON. Повторный запуск во время обработки отключён.

В GUI следует читать не только цвет результата, но и состояние проверки. Серый неполный результат означает, что часть данных получить не удалось. Причины показывают, что именно найдено, а ограничения - что осталось неизвестным. Например, недоступный сайт можно повторно проверить позже, отсутствие OCR исправить установкой моделей, а требование закрытого облачного документа выяснить вручную. Сохранённый JSON удобен для сопоставления повторных запусков.

Для нового Windows-окружения:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[api,ocr,active,dev]"
.\.venv\Scripts\python.exe -m antiphish setup-ocr
.\.venv\Scripts\python.exe -m antiphish update-feeds
```

Для deep устанавливается `.[deep]` и заранее размещаются веса. У установленного пакета данные по умолчанию находятся в `%LOCALAPPDATA%\AntiPhish` или Linux `$XDG_DATA_HOME/antiphish`, иначе `~/.local/share/antiphish`. Исходный проект использует свой каталог. Переопределения: `ANTIPHISH_DATA_DIR`, `ANTIPHISH_MODEL_DIR` и CLI `--kb`.

### 12.2 Одиночная проверка

```powershell
python -m antiphish analyze C:\Mail\message.eml --profile quality --network offline --output C:\Mail\result.json
python -m antiphish analyze C:\Mail\message.eml --profile quality --network http
python -m antiphish analyze C:\Mail\message.eml --network browser --confirm-browser-risk I_UNDERSTAND
python -m antiphish analyze C:\Mail\message.eml --profile deep --network offline
```

`--json` выводит JSON, `--output` сохраняет файл, `--persist` добавляет историю. Вход `-` читает stdin; сырые MIME-байты и кодировку нужно сохранить. Exit codes: 0 - NOT_DETECTED, 10 - SUSPICIOUS, 20 - PHISHING, 30 - анализ не выполнен. Частичность проверяется по JSON.

### 12.3 Linux и Docker

```bash
python3 -m venv .venv
.venv/bin/pip install -e '.[api,ocr,active,dev]'
.venv/bin/python -m playwright install --with-deps chromium
.venv/bin/python -m antiphish setup-ocr

```

GUI требует Tkinter и графического окружения; headless CLI их не импортирует. Браузер переопределяется `ANTIPHISH_BROWSER_EXECUTABLE`.

Compose публикует localhost:8000, использует непривилегированного пользователя, read-only систему, /tmp, отдельный том данных и read-only models/samples. ## 13 Пакетная обработка и обслуживание

Папка просматривается рекурсивно. ZIP/TAR читаются без записи недоверенных путей на диск. Поддерживаются форматы Analyzer; README, JSON-реестры и неподдержанные файлы не анализируются. Вложенный ZIP остаётся одним объектом с собственными дочерними вложениями.

```powershell
python -m antiphish batch C:\Mail --output reports\mail.json
python -m antiphish batch C:\Mail\letters.zip --extensions .eml --output reports\mail.json
python -m antiphish batch C:\Mail\letters.zip --extensions .eml --output reports\mail.json --resume
python -m antiphish update-feeds
python -m antiphish feed-status
python -m antiphish import-domains C:\Data\security-allowlist-domains.csv
```

Для архива с исходниками и копиями писем пригоден `--pattern '*/eml/*'`. Иначе обе копии могут стать объектами. Идентификатор учитывает имя, содержимое и повторение имени; идентичные байты одного формата обрабатываются один раз и отмечаются `duplicate_of`.

Рядом с итогом пишется JSONL после каждого объекта. Возобновляются только COMPLETE с совпадающими байтами, профилем, лимитами, исходниками, каталогом и данными. PARTIAL выполняется снова. Учитываются календарная дата решения и часовая давность сетевого результата. Прерванная последняя строка не мешает предыдущим.

Пакет ограничен 2 000 объектами и 200 МиБ, отдельный файл - 50 МиБ. Небезопасные пути, symlink/junction, шифрование и ошибки отражаются отдельно. Пустой пакет и общий лимит дают ненулевой код CLI; ошибка одного файла не прерывает остальные.

Статистику пакета нужно читать вместе со списком результатов. Число найденных файлов, успешно обработанных объектов, дублей и пропусков отвечает на разные вопросы. Сводка по причинам показывает распространённые сценарии, но одно письмо может иметь несколько причин, поэтому их сумма не равна числу писем. Для последующего поиска используется ID объекта; одного имени недостаточно, поскольку в архиве могут быть повторные имена. Возобновление проверяет содержимое, а не только путь.

`import-corpus` добавляет образцы, `learn-template --label phishing|benign` - проверенный HTML. Перед меткой проверяются реальная цель и получатель; ошибка или промежуточная страница не объявляется атакой по папке. Каталог и модель после изменения требуют перезапуска API. Планировщика нет: обновления можно запускать отдельно средствами ОС.

## 14 JSON Python и REST API

### 14.1 Отчёт и история

Схема отдельного отчёта остаётся 2.0 при версии приложения 2.1. Есть `configuration`, `input`, `verdict`, `analysis_status`, `reason_codes`, `urls`, `pages`, `routes`, `attachments`, `brands`, `fingerprints`, `reputation`, `model_evidence`, предупреждения и `timings_ms`. Формы находятся внутри соответствующих элементов `pages`.

Причина содержит код, серьёзность, источник, детали и область. Время разбито на извлечение, сеть, базы/бренды, модели и решение. Runtime-манифест записывает версии, SHA исходников/каталога и состояние баз/весов. Дата и возраст сохраняются как данные воспроизводимости в JSON.

Batch содержит `results` и `statistics`: ID, путь, SHA256, полный `report`, время, дубли, возобновление, количества статусов/вердиктов, сетевые состояния, P95 и причины по объектам. FAILED не попадает в число отрицательных вердиктов. `elapsed_seconds` учитывает обработку и промежуточный журнал; окончательная сериализация отдельно измеряется в скрипте производительности.

`--persist` сохраняет JSON в `reports/history.sqlite`, но не исходный MIME. В REST история включена по умолчанию. Возвращается `report_id`; хранение не означает независимой проверки метки.

### 14.2 Прямой вызов

```python
from antiphish.analyzer import Analyzer

analyzer = Analyzer()
report = analyzer.analyze(
    r"C:\Mail\message.eml",
    profile="quality",
    network="offline",
)
payload = report.to_dict()
```

Постоянный экземпляр сохраняет подготовленные ресурсы и модели. Собственный `fetcher` позволяет воспроизводить записанные ответы без живой сети. Внешний процесс решает, что делать с предупреждением или PARTIAL: анализатор сам не доставляет письма и не перемещает их в карантин.

### 14.3 Внутренний API

`python -m antiphish serve` запускает localhost:8000; Swagger - `/docs`. Адрес/порт задаются `ANTIPHISH_API_HOST` и `ANTIPHISH_API_PORT`. Авторизации нет; API предназначен для внутреннего использования.

| Метод и путь | Назначение |
|---|---|
| POST /analyze | URL или путь на машине сервера. |
| POST /analyze/file | Multipart-файл. |
| POST /batch | Папка/архив на машине сервера. |
| POST /batch/file | Загруженный архив. |
| GET /reports | Последние результаты без полного тела. |
| GET /reports/{id} | Сохранённый JSON. |
| GET /health | Версия и runtime-состояние. |
| GET /knowledge | Размеры таблиц и возраст репутации. |
| GET /reasons | Коды причин. |

Пример тела: `{"source":"/inputs/message.eml","profile":"quality","network":"offline","persist":true}`. Browser требует `confirm_browser_risk:"I_UNDERSTAND"`. Для POST /batch есть `extensions` и `pattern`; загрузка POST /batch/file принимает `extensions` через запятую без параметра `pattern`.

Путь в JSON относится к файловой системе сервера, поэтому файл с компьютера клиента отправляется через `/analyze/file`. В Docker путь должен быть доступен внутри контейнера. У multipart настройки передаются отдельными полями формы; обычный JSON рядом с файлом не используется. Единичный вызов возвращает оболочку с `report_id` и `report`, пакетный - результаты и статистику.

HTTP-успех сам по себе не означает безопасное письмо. Клиент отдельно читает `verdict`, `analysis_status`, причины и предупреждения. PARTIAL можно направить на повторную или ручную проверку; FAILED нельзя учитывать как отрицательный результат. Если для задачи достаточно извлечения без сохранения истории, в запросе устанавливается `persist:false`.

Сервер ждёт результат и сериализует анализы одним lock, чтобы не смешивать бюджеты OCR и GPU. Брокера нет; большой пакет удобнее CLI с журналом. Загрузка ограничена 50 МиБ с небольшим multipart-запасом; контроль действует и для chunked-запроса до распаковки multipart.

## 15 Что известно о качестве

### 15.1 Проверки реализации

Последний сохранённый Windows-прогон: 143 успешных теста. Linux: 141 успешный и два пропуска - Windows GUI и недоступные там исходные архивы. Это проверки форматов, URL, сетевой безопасности, форм, русских сценариев, OCR, моделей, API и GUI; они не заменяют независимую разметку почты.

### 15.2 Письменный набор

Основная часть переданного ZIP - 540 писем: 40 phish и 500 benign. Вне неё есть пять объектов для пересмотра и четыре robustness. Среди benign 468 писем Linux-рассылки и 32 старых SpamAssassin; среди phish 32 ранее изучавшихся target_brands и восемь Nazario. Поэтому весь набор нельзя считать полностью незнакомым.

Групповая полнота предупреждений - 73,9%. Wilson 95% для обычного recall: 70,9–92,9%; верхняя граница FPR при 0/500 - 0,762%. Наблюдаемый ноль не доказывает отсутствие будущих ошибок. После просмотра и исправлений это материал разработки, а не новый независимый тест.

Deep проверен на всех 40 phish и 40 benign, выбранных хешем ID без отбора по вердикту. Он дал 35/40 предупреждений, 0/40 строгих PHISHING и 0/40 ложных тревог; 78 COMPLETE, два PARTIAL. Добавлено одно выявление к quality. Один ответ Qwen имел INVALID_JSON. Верхняя граница FPR для столь маленьких 40 benign - 8,76%.

### 15.3 Корпус со страницами

Полный архив: 396 писем и 556 HTML. Offline-письма дали 44 SUSPICIOUS; записанные маршруты - 49 SUSPICIOUS и четыре PHISHING. Остальные без достаточных признаков. Для маршрутов 42 COMPLETE и 354 PARTIAL: записанных ответов часто недостаточно для всего обхода.

В российском срезе 42 письма: 31 предупреждение локально и 33 с доступным маршрутом. Достигнуты 27 из 35 страниц; пять маршрутов COMPLETE, 37 PARTIAL. Группа выделена по бренду, не независимой языковой разметкой. Эти числа нельзя объявлять истинным recall по непроверенной метке поставщика.

### 15.4 Независимые и текущие страницы

Первый срез PhreshPhish содержал шесть phish и 14 benign. Исходные две ложные тревоги на eBay и закрытом password-dialog PDF.js устранены; затем тревог не было, но ни одна из шести положительных меток тоже не выявлена. Этот срез использован для исправлений.

На следующих 64 ранее не просмотренных страницах - 29 phish и 35 benign - статические правила дали 0/29 и 0/35. 56 COMPLETE, семь PARTIAL, один FAILED. Правила по этому результату не настраивались. Есть ошибки, блоги, статьи-приманки и неизвестные бренды; исходные метки оставлены в знаменателе и требуют независимого пересмотра. Это слабая переносимость, а не успех детектора.

Свежие официальные российские корни: 33 попытки, 18 HTML, 15 недоступно; тревог 0/18, но семь проверок PARTIAL. Свежие OpenPhish: 40 попыток, 20 снимков, один с несовпавшим хешем оставлен FAILED. С пустой KB результат - один PHISHING и один SUSPICIOUS из 20. Русских URL в этом срезе нет. Доступность и URL-метка провайдера не подтверждают содержимое страницы.

### 15.5 Метрики и пригодность данных

В 540-наборе 305 писем относятся к старым данным, у девяти phish обнаружены адреса-примеры, у двух - нет навигационного URL. Аудит первых 120 из 717 уникальных адресов: 34 получены, 35 недоступны, 51 пропущен как личный/токенизированный или пример. Это не полный контроль доступности.

`benchmark-dataset` считает строгий PHISHING и сумму PHISHING+SUSPICIOUS отдельно, публикует полноту, источники, языки, группы, Wilson и парное сравнение. Ошибки остаются в знаменателе. Проверенные независимые метки имеют отдельный блок; сейчас таких меток в переданном наборе нет. Разбиение уже просмотренного корпуса не создаёт новый holdout.

Старый контроль 4 150 SpamAssassin ham дал ноль тревог, но не доказывает качество современной российской почты. Для этого нужны независимо размеченные банковские, торговые, служебные и государственные письма. Сохранённый снимок делает версии сравнимыми; живое посещение отдельно измеряет доступность, а не ежедневно меняет смысл метки.

Recall показывает долю обнаруженных размеченных атак, FPR - долю тревог на обычных объектах, precision - долю размеченных атак среди тревог. Precision зависит от состава выборки: набор с большим числом атак не воспроизводит обычный почтовый поток. Поэтому единую accuracy нельзя использовать как главный показатель, особенно когда легитимных писем значительно больше.

Групповая оценка уменьшает влияние многочисленных копий одной кампании. Парное сравнение использует одни и те же ID и метки; доверительный интервал показывает неопределённость, а не обещает такой результат на любом другом источнике. Отдельно проверяются качество извлечения и полнота обхода: низкое обнаружение может быть связано как с правилом решения, так и с недостигнутой целевой страницей.

Deep прошёл 80 писем с пустой KB. Сеть и экспериментальный классификатор выключены; дубли и возобновлённые результаты не использованы для оценки первичного анализа.

### 16.2 Сетевая стоимость и постоянный процесс

Прежний отдельный эксперимент на 42 российских письмах дал около 1 274/мин fast, 658/мин quality и 7,48/мин deep. Он использует другую серию и версию; сравнение с новым batch не доказывает ускорение алгоритма. Размеры писем были 2,7–307,1 КиБ, медиана 17,6 КиБ.

Контроль одного публичного example.com с лимитом одной страницы занимал примерно 0,27 с HTTP, 3,30 с browser и 14,36 с deep/browser. Ограниченный обход не равен полной проверке всех ссылок. На синтетической многошаговой банковской форме прежняя серия занимала около 3,97 с и подтверждала блокировку тестового секрета. Это стоимость конкретного сценария, а не живого фишингового сайта.

Отдельный старый холодный CLI deep занял 70,07 с, включая импорт и первую загрузку. Новый первый объект измерен внутри другого постоянного процесса, поэтому эти числа напрямую не сравниваются. Открытый GUI, API и batch сохраняют модель; отдельная команда на каждое письмо загружает её снова.

При конкуренции за GPU первоначальный deep-прогон был прерван на четырёх объектах. Он не используется как завершённый тест скорости. Новый цельный прогон выполнен после освобождения памяти. CPU-only deep и GPU в Docker не измерены.

### 16.3 Повторение и интерпретация

```powershell
python docs\benchmark_revision.py --dataset letters.zip --output-dir reports\check
python -m antiphish benchmark-dataset letters.zip --kb empty.sqlite --output reports\quality.json
python -m antiphish audit-dataset letters.zip --output-dir reports\audit --check-links --max-urls 120
python -m antiphish capture-urls urls.txt --output-dir data\private\captures --max-urls 100
```

Первая команда выполняет quality и fast/quality batch; deep не запускает. ZIP требует `manifest.jsonl` с ID, путём, меткой, желательно SHA256, источником, языком и группой. Для HTML нужен исходный URL. Поддерживаются `evaluation_path` и `sha256_evaluation`.

Каждая строка manifest описывает один объект. `path` указывает файл внутри архива, `label` принимает phishing или benign, `group_id` объединяет близкие примеры. Для отдельно подготовленного HTML используются поля evaluation, чтобы сохранить исходный объект. `review_status:independently_verified` отмечается только после самостоятельной проверки человеком; копирование метки поставщика не подходит. `label_basis` объясняет основание, а `source`, `language` и `brand` позволяют анализировать срезы.

Проверку доступности следует выполнять отдельно от проверки детектора. Страница с ответом 200 может оказаться парковкой, ошибкой, законной промежуточной страницей или новым содержимым. Отсутствие страницы тоже не отменяет историческую атаку. Снимок и его хеш фиксируют исследованные данные; решение о пригодности метки требует просмотра содержимого и контекста сообщения.

Аудит создаёт очередь пересмотра и отмечает старые данные, заглушки и отсутствие адресов. Capture фиксирует HTTP-статус, конечный адрес, заголовок и хеш. Ошибка хранения отличается от сетевого отказа. Полные результаты и версии находятся в `reports/`; точные машинные отметки времени остаются в JSON для воспроизводимости.

## 17 Типичные вопросы и ограничения

Если известное письмо не получило PHISHING, проверьте источник индикатора, полноту маршрута, видимость формы и установленный получатель. Непроверенный корпусный хеш или внешний домен недостаточны для сильного решения. Сначала нужно понять, какого факта не хватает, а не добавлять всё название домена в блокировку.

При неожиданном предупреждении смотрите код, область и цитату. Форма могла быть законной сторонней авторизацией, текст - новостью, а отправка - обычной анкетой. Подтверждённый отрицательный шаблон исправляет сходство, но не отменяет независимый IOC. Один отрицательный пример не разрешает весь бренд или хостинг.

Длительный анализ обычно связан с сетью, запуском браузера, изображениями, OCR или загрузкой модели. Сравнивать нужно одинаковые входы и настройки. Несколько процессов deep создают несколько экземпляров весов и могут исчерпать GPU; увеличение параллелизма не гарантирует ускорение.

CAPTCHA, закрытые документы, геомаскировка, истёкшие URL и серверозависимый вход могут скрыть цель. Некоторые Office-форматы и шифрование исследуются частично. Буквальная декодировка не заменяет полноценный анализ произвольного JS. Offline-HTML не означает рендер всех зафиксированных ресурсов.

Программа не является почтовым шлюзом, антивирусной VM или системой круглосуточного мониторинга. Макросы не исполняются, несколько регионов не проверяются, модели автоматически на решениях пользователя не обучаются. Телефонное мошенничество и смена реквизитов без поддельной формы могут требовать внешней истории и ручной проверки.

## 18 Сопровождение и дальнейшая работа

Главная потребность - современная независимо размеченная российская почта с близкими обычными и опасными случаями. Нужно фиксировать момент подтверждения, происхождение, конечную страницу, форму и получателя. Новые кампании отделяются по времени и шаблону; повторные копии не должны повышать оценку переносимости.

Для нового правила сохраняются положительный пример и близкий отрицательный: нормальная акция, законная форма, счёт или сторонний вход. Для бренда проверяются домены, SSO и партнёры. Отдельно нужна ручная эталонная разметка извлечения ссылок, QR, форм и логотипов: прохождение unit-тестов её не заменяет.

Код тайм-аута браузера исправлен и проверен повторным запуском в том же процессе. Однако сложная обфускация, серверные шаги, антибот и полный offline-рендер остаются направлениями развития. Для логотипов нужны реальные области и отрицательные примеры; для смены LLM - независимое сравнение при одинаковом бюджете.

Перед передачей сохраняются конфигурация, каталог, отчёты, снимки и версии весов. JSON-журнал включается `--log-json` и идёт в stderr без тела письма и навигационных токенов. Машинные отметки времени нужны для срока действия и повторения проверки.

Перед публикацией следует проверить приватные данные: новый .gitignore не удаляет ранее отслеживаемые базы и историю Git. Текущие ограничения и задачи продолжения собраны в `WORK_STATUS.md`.
